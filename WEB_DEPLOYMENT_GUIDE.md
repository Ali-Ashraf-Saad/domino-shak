### 3.1 Corrected asset paths and the Asset Links rule

- The sync script copies fonts into **`fonts/`** and PeerJS into **`vendor/`** so the game's relative paths resolve. An earlier attempt used an `assets/` prefix, which caused **404s** for fonts and `peerjs.min.js`; that was fixed. Verify these two directories exist after every sync.
- **The script does not create a production `assetlinks.json` when `PLAY_APP_SIGNING_SHA256` is not supplied.** In that case it removes any existing `assetlinks.json` and warns that only `assetlinks.json.template` is present. There is deliberately **no placeholder `assetlinks.json` in the generated folder**. Do not invent one and do not upload a placeholder — Android would reject it.
- A real `assetlinks.json` is written only when the environment variable `PLAY_APP_SIGNING_SHA256` supplies a valid 32-byte hex Play App Signing fingerprint. That fingerprint is **not available** in this environment, so no real file was generated.
- `SHA256SUMS.txt` lists generated files but excludes `.well-known/assetlinks.json`.

Sync-script behaviour (implemented, not design-only): read-only from `domino_shak_app/assets/web/`; never writes the historical `index.html`; fails clearly if the canonical source is missing; idempotent; keeps paths relative; contains no secrets or credentials.

## 4. Hosting capabilities and restrictions

Observable facts from the Phase 0 audit:

- Static HTML/CSS/JS is served correctly.
- HTTPS is available with a valid certificate.
- The **old** site loaded CDN scripts and Google Fonts; the generated build uses bundled assets instead.
- The site is behind a **JavaScript cookie challenge**. Plain HTTP clients are stopped; a real browser executes the challenge.
- `/.well-known/assetlinks.json` is currently absent on the host. After the challenge cookie is set, the path reaches an InfinityFree 404 page.
- No PHP endpoint is used by the game.

Hosting support is: **PHP / HTML / CSS / JS only**. No Node, Python, or custom server. Therefore:

- do not design a deployment step that needs a long-running process;
- do not assume a WebSocket server can be started on the host;
- room invitations stay static `?room=CODE` URLs;
- online multiplayer keeps using PeerJS cloud signalling and WebRTC;
- offline LAN must work without the public host (see `LAN_MULTIPLAYER_ARCHITECTURE.md`).

PHP/DB support is **unknown**. A backend would only be needed for a future moderation/review flow, which is not approved.

### 5.1 FTPS deployment runbook — executed successfully

**Status: tool implemented, credentials entered by the maintainer in a hidden
local prompt, deployment completed and verified on the public host.**

A deployment helper at `tools/ftps_deploy.py` was used for the live upload. It
gives the maintainer a hidden local prompt, so no credential value was handled by
the agent or written to the repository.

Execution record (2026-11-19):

- Live root: `/liardominoes.gt.tc/htdocs`; staging: `<root>/_staging`.
- Backup 1 `deployment_backups/20261119-162401` (23 files) captured the original
  live `index.html` (`d9d711ea…`) plus the staging build.
- Staging upload: 22 files; staging verified in a browser before promotion.
- First promotion succeeded, but an immediate rollback restored the original
  `index.html`, so the live site briefly reverted to the old build.
- Backup 2 `deployment_backups/20261119-163831` (44 files) captured that state.
- Second promotion succeeded: 22 managed files copied into the live root, with
  **no remote deletions**. Final live verification passed (§6/§7).
- Rollback was therefore exercised in practice and works; it must not be run
  after a promotion unless a revert is actually intended.

Transport properties (verified, not assumed):

- Explicit **AUTH TLS on port 21**, then `PROT P` for the data channel. There is
  no code path that transmits credentials over plaintext FTP.
- Certificate **and hostname** are verified with `ssl.create_default_context()`
  (`CERT_REQUIRED`, `check_hostname=True`, TLS >= 1.2). Verification failure
  aborts; the script never disables it.
- Credential-free pre-flight check on 2026-11-19 returned
  `TLSv1.3`, `CN=ftpupload.net`, SAN `ftpupload.net` / `www.ftpupload.net`,
  `Verification: OK`. This did not authenticate or transfer any files.

Credential handling:

- The script refuses to run unless stdin is an interactive TTY. It prompts with
  `getpass` (hidden input) and keeps the values only in process memory.
- No credential is written to a file, placed in `argv` or the environment, or
  printed. The tool file itself contains no credentials.

Run it in your **own terminal** (the agent never sees the credentials):

```bash
cd /home/ali/Documents/DominoGame
python3 tools/ftps_deploy.py
```

Recommended order inside the menu:

1. **Inspect** remote structure (read-only). Confirm the document root, commonly
   `/htdocs` on this host, and note unrelated files that must be preserved.
2. **Set / confirm live web root** to that absolute path. The tool derives the
   staging path `<root>/_staging`.
3. **Back up live site.** Files are downloaded to
   `deployment_backups/<timestamp>/` with a `BACKUP_SHA256SUMS.txt` manifest.
4. **Upload build to staging.** Verify in a real browser at
   `https://liardominoes.gt.tc/_staging/` using the §6 checklist before any
   promotion.
5. **Promote staging -> live** only after staging verification. Promotion copies
   only the managed files listed in §3 (and `fonts/` + `vendor/`) and **deletes
   nothing** on the host, so unrelated files survive.
6. **Rollback** if the live verification fails: restore the chosen
   `deployment_backups/<timestamp>/` over the live root. This overwrites the
   managed files with their pre-deploy bytes; files added after the backup are
   reported but not deleted, so review them manually.

Do not upload `assetlinks.json` from staging; only the template exists, and a real
file requires the Play App Signing fingerprint (§3.1).
